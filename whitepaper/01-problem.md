# 问题与约束

## 四个硬约束

Interisle 的设计从四条约束出发，它们不是需求列表，而是不可回避的边界：

1. **访客端是最小的独立服务器**，其他访客可以访问它。
2. **物品、能力具有互通性**：A 服获得的东西能在 B 服使用。
3. **服务器独立、可自定义**，权限在服主手中，服务器数量不确定。
4. **访客的数据和物品随身**；从 A 带出的物品可以带到任何地方，同时 A 服承认它已被带走。

这四条放在一起，意味着系统不能假设：有一个全球可信的中心、所有服务器跑同一款游戏、物品的数据结构一致、服务器之间实时在线、世界内位置可以被一个全局数据库实时跟踪。

## 现有方案各缺一块

**共享数据库**（多个服务器连同一个 MySQL/Redis）把“唯一数据源”交给一个库，简单直接，但跨组织时没人愿意把库存交给别人；数据库故障时所有服一起停。

**中心资产 API** 能解决存储和分发，但只做“上传—下载”的 API 不解决跨游戏语义。A 的“传说之剑”下载到 B，B 的引擎里没有这个实体。中心必须承担翻译，或者承认它只做同构同步。

**纯 P2P、DHT、Gossip** 去掉了中心，但带来双花窗口、节点发现、NAT 穿透和离线体验的成本。对“随身携带”这种低频、高价值的操作，这些成本通常不划算。

**NFT/区块链** 能提供跨平台确权，但把资产绑在链上，带来加密钱包、Gas、治理和合规负担；而且它解决的是“所有权记录”，不是“B 游戏认不认这个物品”。

## Interisle 的拆分

Interisle 不试图用一个组件跟踪所有东西，而是把职责拆开：

| 职责 | 放在哪 |
|---|---|
| 世界内物品、位置、容器、掉落、销毁 | 游戏服务器（isle） |
| 当前会话的背包、进出背包 | 游戏服务器（isle） |
| 随身所有权 | 玩家仓库里的签名凭证 |
| 凭证双花防护 | coordinator（每个社区一个 claim domain） |
| 社区信任名单、节点目录 | coordinator |
| 跨游戏物化 | 目标服的适配器；优先使用本游戏原生快照，否则从 descriptor 创建 |
| 本地表现 | 凭证中的 presentation 引用；资源由本地解析，不随物品转移 |
| 玩家身份 | 账号 DID；角色是账号下的标签 |

关键判断：

- **世界和背包属于游戏服务器。** 物品在哪个坐标、哪个容器、是否被销毁，只有当前 isle 知道；协议不跟踪，也不要求上报。进入 isle 时玩家从仓库选择凭证兑换，commit 后物品进入该 `(owner, character)` 的会话背包；只有背包物品能提取。
- **仓库只保存凭证。** 一张凭证代表一整件物品；它在仓库里时，世界里不能同时存在同一件物品。会话背包是 isle 的本地物品集合，不是第二份凭证存储。
- **coordinator 只防止本 claim domain 内的凭证双花和实例分叉。** 它记录 `CLAIMABLE` / `RESERVED` / `SPENT` 和 `(claim_domain, instance_id)` 的 head，不保存事件日志，不知道物品在世界里的位置，也不解释物品语义。不同社区的中心不共享 claim 状态。
- **物化权属于目标服。** B 的服主决定接不接受、怎么用原生快照或 descriptor 创建物品、怎么显示；v1 不要求生成签名解释报告。
- **跨游戏不是能力等价。** v1 没有能力凭证，也不执行源游戏的代码；目标适配器只负责保留身份和原生数据。
- **源 isle 是受信的。** 协议防止同一张凭证在同一个 claim domain 内被花两次，不能阻止游戏服自己复制或丢失物品；那是服务器运营和游戏逻辑的责任。

## 设计原则

1. 没有签名的对象，不改变跨服状态。
2. 一张凭证在一个 claim domain 内只能花一次，一个实例只能有一条有效 head；coordinator 是这条规则的执行点。跨域必须走显式转移，不能直接 claim。
3. 提取不需要 coordinator，但只对打开会话背包中的本地物品生效；兑换必须经过 coordinator。coordinator 不可达时兑换失败关闭，不静默降级。
4. 数值用整数/定点数，禁止浮点，保证跨语言签名一致。
5. 跨游戏允许有损；v1 保证身份、origin 和逐游戏原生数据可追溯，不保证能力等价。
6. 协议版本化；破坏性变更走新 major，不偷偷改语义。
